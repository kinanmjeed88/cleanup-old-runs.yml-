# المراجعة الإضافية لتدفق تنظيف تشغيلات GitHub Actions

- **التاريخ:** 2026-11-03
- **المستودع المركزي:** `kinanmjeed88/cleanup-old-runs.yml-`
- **فرع العمل:** `arena/cdeeccea-cleanup-old-runs-yml`
- **الفرع الافتراضي المنشور:** `searchidf`

**الحالة:** اكتملت المراجعة والتصحيحات والاختبارات المحلية. **لم يُنفَّذ أي حذف حقيقي، ولم تتحول الجدولة إلى live.**

---

## 1. الخلاصة التنفيذية

| السؤال | النتيجة |
|---|---|
| السبب الدقيق لـ`DRY RUN` في التشغيل الموثّق | التشغيل جاء من **`schedule`**، وهذا المسار يفرض `dry-run` عمداً قبل قراءة أي اختيار يدوي. |
| هل كان التشغيل `workflow_dispatch`؟ | لا، التشغيل الذي طابقناه في GitHub كان `schedule`. توجد تشغيلات يدوية أقدم في السجل، لكنها ليست مصدر هذا الدليل. |
| هل الافتراضي `dry-run`؟ | نعم، في `workflow_dispatch` وفي Python CLI. هذا افتراض آمن، وليس عطلاً. |
| هل يوجد شرط يجبر كل التشغيلات على dry-run؟ | لا. الشرط الإجباري يخص `schedule` فقط. اليدوي يستطيع اختيار `live` مع `confirm_live=DELETE`. |
| هل ضاعت قيمة `mode` بين workflow وPython؟ | لا. أثبت اختبار تنفيذ فعلي لخطوات Bash أن `live` تصل إلى `--mode live` ثم إلى منفّذ الحذف. |
| سياسة الاحتفاظ بعد التصحيح | **50 تشغيلاً مكتملاً لكل مستودع**، في workflow وshell fallback وPython CLI وسياسة الاحتفاظ والاختبارات والوثائق النشطة. |
| هل `Actions: write` متوفرة فعلياً في `CLEANUP_TOKEN`؟ | **غير متحقق منها حتى الآن.** لا يمكن استنتاج ذلك من فحوص القراءة الحالية، ولا يجوز إعلانها متاحة دون دليل. |
| هل نُفّذ حذف حقيقي؟ | **لا.** اختبارات live استخدمت API Fakes فقط. الاستعلامات الحقيقية في المراجعة كانت قراءة فقط. |

**النتيجة المهمة:** حتى لو كان `CLEANUP_TOKEN` يملك `Actions: write`، فإن التشغيل المجدول سيبقى `DRY RUN`. حالة الصلاحية ليست سبب اختيار الوضع في الدليل المرفق.

## 3. تتبع التنفيذ من GitHub Actions إلى دالة الحذف

المسار الحالي بعد التصحيح:

```text
.github/workflows/cleanup-old-runs.yml
  on: schedule | workflow_dispatch
    ↓
  Resolve run mode
    schedule                         → mode=dry-run دائماً
    workflow_dispatch + dry-run      → mode=dry-run
    workflow_dispatch + live + DELETE→ mode=live
    live بدون DELETE / قيمة غير صالحة→ فشل قبل تشغيل Python
    ↓
  Run central cleanup
    --mode "${RUN_MODE:-dry-run}"
    --keep-latest "${KEEP_LATEST:-50}"
    [--confirm-live DELETE عند live]
    [--skip-branches عند اختيار تنظيف التشغيلات فقط]
    ↓
tool/central_cleanup.py
  build_parser() → main()
    يفحص --mode live + --confirm-live DELETE
    ويرفض live إذا GITHUB_EVENT_NAME=schedule
    ↓
  CleanupOptions(mode, keep_latest=50)
    ↓
  CentralCleanup.process()
    check_repository_access() فحوص قراءة
    ↓
  CentralCleanup._process_runs()
    fetch_all_runs() بكل الصفحات
    plan_retention() يحتفظ بأحدث 50 مكتملة
    apply_retention(..., dry_run=...)
    ↓
tool/run_retention.py::apply_retention()
  dry_run=True  → يسجل would delete فقط، لا يستدعي الحذف
  dry_run=False → يستدعي client.delete_workflow_run()
    ↓
tool/github_client.py::delete_workflow_run()
  DELETE /repos/{owner}/{repo}/actions/runs/{run_id}
```

### مواضع الكود الأساسية

| الموضع | الدور |
|---|---|
| `.github/workflows/cleanup-old-runs.yml:16–56` | triggers، اختيار `mode`، الافتراضي 50، وخيار `skip_branches`. |
| `.github/workflows/cleanup-old-runs.yml:104–143` | فرض dry-run للجدولة، وقبول live اليدوي فقط مع `DELETE`، ورفض القيم غير الصالحة بدلاً من إسقاطها صامتاً إلى dry-run. |
| `.github/workflows/cleanup-old-runs.yml:145–175` | تمرير `RUN_MODE` و`KEEP_LATEST` إلى Python، وتمرير `--skip-branches` عند طلبه. |
| `tool/central_cleanup.py:826–844` | بوابة الأمان الثانية في CLI: التأكيد النصي ومنع live المجدول. |
| `tool/central_cleanup.py:536–554` | قراءة التشغيلات، بناء خطة الاحتفاظ، ثم استدعاء منفّذ الحذف. |
| `tool/run_retention.py:30` | `DEFAULT_KEEP_LATEST = 50`. |
| `tool/run_retention.py:189–253` | فرز المكتملة فقط واختيار أحدث 50 لكل مستودع. |
| `tool/run_retention.py:338–382` | المحاكاة أو الحذف الفعلي؛ أول 401/403 يوقف بقية حذف ذلك المستودع. |
| `tool/github_client.py:292` | استدعاء DELETE الخاص بتشغيل واحد. |

### ماذا كان يحدث في التشغيل الموثّق؟

1. `github.event_name` كان `schedule`.
2. دخلت خطوة `Resolve run mode` فرع الجدولة.
3. كتبت `mode=dry-run` في `GITHUB_OUTPUT` وخرجت قبل منطق الاختيار اليدوي.
4. وصلت `RUN_MODE=dry-run` إلى Python.
5. أنشأ CLI وضع `DRY RUN`.
6. وصلت الخطة إلى `apply_retention(..., dry_run=True)`.
7. لذلك بقي `runs_deleted=0` و`runs_failed=0`؛ لم تُستدعى دالة الحذف أصلاً.

هذا يفسر الدليل دون الحاجة إلى افتراض عطل في تمرير المدخلات أو نقص صلاحية الكتابة.

## 4. صلاحية `Actions: write`

### ما تثبته الكود والأدلة

- `actions:read = verified`: فحوص القراءة تستطيع سرد التشغيلات.
- `actions:write = unverified`: يضيفها `check_repository_access()` صراحةً لأن استجابات قراءة المستودع/التشغيلات لا تكشف منحة `Actions: write` الخاصة بالرمز.
- `permissions.push/admin/maintain` في بيانات المستودع مؤشر كتابة عام، **وليس دليلاً على صلاحية Actions write**.
- كتلة `permissions: contents: read` في workflow تخص `GITHUB_TOKEN` الخاص بالـworkflow، ولا تمنح أو تنزع صلاحيات `CLEANUP_TOKEN`. لذلك لا نصحح هذه المسألة بإضافة `actions: write` إلى token الـworkflow.

### ما لم نستطع إثباته بأمان

قيمة `CLEANUP_TOKEN` غير موجودة في بيئة المراجعة، ولم نقرأ قيمة السر. محاولة قراءة أسماء الأسرار برمز الجلسة أعادت 403، ولا يجوز استخدام تلك النتيجة للحكم على صلاحيات الرمز السري نفسه. عليه:

> **لا يوجد دليل كافٍ الآن يقول إن CLEANUP_TOKEN يملك Actions: write، ولا دليل يقول إنه لا يملكها. الحالة الصحيحة: unverified.**

### التحقق دون حذف تجريبي

على مالك الرمز مراجعة إعدادات الرمز في GitHub:

1. Settings → Developer settings → Personal access tokens.
2. فتح الرمز المستخدم في `CLEANUP_TOKEN` دون نسخه إلى المحادثة أو التقارير.
3. التأكد من أن Repository access يشمل `kinanmjeed88/Scan-id` والمستودعات المعتمدة.
4. التأكد من **Repository permissions → Actions: Read and write**.
5. التأكد من عدم انتهاء الرمز، ومن أي اعتماد مطلوب على مستوى المؤسسة.
6. إن لزم تحديث السر، تحديث Repository secret `CLEANUP_TOKEN` في المستودع المركزي.

عند أول حذف حقيقي **بعد الموافقة** تصبح استجابة API هي نقطة الإنفاذ: نجاح DELETE يثبت القدرة العملية على ذلك التشغيل، و401/403 يوقف بقية المحاولات في ذلك المستودع ويظهر في التقرير والسجل وexit code.

## 5. التصحيحات المنفذة

### سياسة 50

جرى البحث في كل مواضع التعريف والتمرير، وتوحيد المصادر النشطة:

- `workflow_dispatch.inputs.keep_latest.default = "50"`.
- shell fallback `${KEEP_LATEST:-50}`.
- `DEFAULT_KEEP_LATEST = 50`.
- `CleanupOptions` وPython CLI يستخدمان الثابت نفسه.
- تحديث اختبارات الحدود والأعداد والافتراضات. بقيت اختبارات `keep_latest=20` صريحة حيث يلزم لإثبات أن التجاوز اليدوي ما زال ممكناً.
- تحديث README والوثائق النشطة. التقارير التاريخية التي تذكر 20 أُبقيت كبيانات تاريخية وأضيفت لها ملاحظة واضحة بأنها ليست السياسة الحالية.

### أمان الوضع اليدوي

- بقيت الجدولة `dry-run` دائماً.
- live اليدوي يتطلب `confirm_live=DELETE` بالضبط.
- القيم غير المعروفة مثل `LIVE` تُرفض بوضوح بدلاً من تحويلها صامتاً إلى dry-run.
- الأحداث غير المدعومة لا تصل إلى التنظيف.
- أُضيف `skip_branches` اختيارياً، افتراضيه `false` للحفاظ على السلوك السابق، ويسمح بمسار **runs-only** عند اعتماد تنظيف التشغيلات دون الفروع.

### وضوح الفشل

رسالة رفض الحذف تذكر الآن رقم التشغيل وHTTP status الفعلي (401 أو 403) واسم المستودع، وتوضح توقف بقية المحاولات. الفشل يظهر في:

- سجل الخطوة كـ`::error::`؛
- تقرير المستودع و`summary.json` وstep summary؛
- حالة `FAILED`؛
- exit code `1`.

### سيناريو live اليدوي بـAPI Fakes

السيناريو يستخدم 739 تشغيلاً مكتملاً في الذاكرة، ويختار `Scan-id` فقط:

```text
event = workflow_dispatch
mode = live
confirm_live = DELETE
repository = kinanmjeed88/Scan-id
keep_latest = 50
```

النتيجة:

- وصلت `--mode live --confirm-live DELETE --keep-latest 50` إلى CLI.
- نُفّذت **689 عملية DELETE وهمية** عبر مسار `GhCliClient.delete_workflow_run` الحقيقي مع transport وهمي.
- بقيت **50** تشغيلات في حالة المستودع الوهمي.
- `runs_failed=0`، exit code `0`، والتقرير `LIVE`.
- المستودعات الأخرى المكتشفة لم تُحذف تشغيلاتها لأن المحدد كان `Scan-id`.
- عند `skip_branches=true`: حُذفت التشغيلات الوهمية ونُفّذت مرحلة الفروع **صفر مرات**.

### سيناريو فشل أول حذف

- أول DELETE وهمي أعاد HTTP 403.
- عدد محاولات الحذف: **1** فقط.
- `runs_deleted=0`، `runs_failed=1`، وبقيت 739 تشغيلات وهمية.
- الحالة `FAILED`، exit code `1`.
- سبب التوقف وذكر 403 و`Actions: Read and write` ظهر في التقرير والسجل وstep summary.
- اختبار منفصل غطى HTTP 401 وأكد ظهور الرقم الفعلي للحالة والتوقف.

### سيناريوهات الأمان

- `schedule` بقي dry-run حتى مع قيم مدخلات live مصطنعة.
- الافتراضي اليدوي بقي dry-run.
- dry-run لم يستدعي DELETE إطلاقاً.
- تأكيد ناقص أو `delete` بأحرف صغيرة أو `yes` أوقف الخطوة قبل Python.
- قيمة وضع غير صالحة وحدث غير مدعوم رُفضا بوضوح.
- غياب `KEEP_LATEST` من البيئة استخدم 50، لا 20.

**كل عمليات الحذف في الاختبارات كانت على كائنات في الذاكرة. لم تتصل الاختبارات بـGitHub ولم تحذف تشغيلاً أو فرعاً حقيقياً.**

## 8. كيفية تشغيل LIVE يدوياً بعد موافقتك

> هذه خطوات مستقبلية، وليست تفويضاً منفذاً الآن. يجب أولاً اعتماد التعديلات ودمجها في الفرع الافتراضي `searchidf`؛ تشغيل الملف من فرع المراجعة وحده لن يمر من حاجز الفرع الافتراضي.

### أ. تحقق آمن ثم معاينة جديدة

1. تأكد من منحة `Actions: Read and write` في إعدادات `CLEANUP_TOKEN` كما في القسم 4.
2. افتح Actions → Central Cleanup → Run workflow على الفرع الافتراضي.
3. شغّل معاينة واحدة:

| المدخل | القيمة |
|---|---|
| `mode` | `dry-run` |
| `repository` | `kinanmjeed88/Scan-id` |
| `keep_latest` | `50` |
| `discovery_mode` | `auto` |
| `discovery_only` | `false` |
| `skip_branches` | `true` |
| `confirm_live` | فارغ |

4. راجع `diagnostics/summary.json` و`diagnostics/reports/kinanmjeed88__Scan-id.json`: الوضع، 50، اكتمال القائمة، المستبعدات، والعدد الجديد للمرشحين. لا تعتمد رقم 718 القديم.

### ب. بعد موافقة صريحة على العدد الجديد

استخدم نفس القيم مع:

```text
mode = live
confirm_live = DELETE
```

واترك `skip_branches=true` إذا كانت الموافقة على **التشغيلات فقط**. لا تستخدم `repository=all` إلا بموافقة منفصلة تشمل كل المستودعات المكتشفة. إبقاء `skip_branches=false` يفعّل أيضاً تنظيف الفروع المدموجة وفق خوارزمية المشروع.

### ج. المراقبة والتوقف

- راقب أول DELETE وعدادات `runs_deleted` و`runs_failed`.
- عند 401/403 يتوقف ذلك المستودع وتُرفع التقارير لأن خطوة الرفع `if: always()`.
- صحح الرمز/الصلاحيات ثم أعد معاينة قبل إعادة live.
